## Context

`flag_accounts_needing_attention` (`account_discovery.py:1463`) scans account-level signals
(spend/efficiency moves, status alerts, and — after the prereq `attention-budget-pacing-flag` —
budget pacing). All of those derive from account-level reads. Detecting **disapproved** or
**active-but-not-delivering ads** requires descending to the **ad level** (a per-account ad
enumeration), which is a materially heavier read surface, so it is gated behind its own opt-in and
bounded to accounts the cheap scan already surfaced.

The ad-level vocabulary already exists in the codebase:
- `monitor.py:67` — `DELIVERING = {"ACTIVE", "IN_PROCESS"}` (an ad's `effective_status` that means it
  is actually running).
- `control.py:83` — `AD_FIELDS = ["id","name","status","effective_status","adset_id","issues_info"]`;
  ad enumeration via `reader.iter_paginated(f"/{ad_account_id}/ads", params={"fields": …, "limit":
  200})` (see `control.scan_issues` at `control.py:1168` and `monitor.py:871`). `issues_info` carries
  Meta's policy/disapproval detail; `control._issue_summaries` (`control.py:97`) reads it.

## Design (resolved)

**Opt-in + already-flagged gate (the read-budget answer).** `flag_accounts_needing_attention` gains
`include_ad_health: bool = False`. When `True`, after the flagged list is finalized (behavior +
pacing flags, severity ≥ medium), fan out into the ads of **only the flagged accounts** via
`fan_out_accounts(read_ads, flagged_account_ids)`. Informational/clean accounts are **not**
ad-scanned. So a full-fleet run pays ad reads only for the handful that surfaced — worst case =
`len(flagged)` ad enumerations, never `200×` unconditionally.

**Import-light discipline.** `account_discovery.py` is deliberately import-light (module docstring
`account_discovery.py:8`) — do **not** `import monitor` (it drags in confidence/control/early_triage/
meta_api). Define the tiny status vocabulary **locally** in `account_discovery.py` with a comment
pointing at `monitor.DELIVERING` as the sibling definition to keep in sync:
```python
_AD_DELIVERING = frozenset({"ACTIVE", "IN_PROCESS"})            # mirrors monitor.DELIVERING
_AD_PAUSE_STATUSES = frozenset({"PAUSED", "CAMPAIGN_PAUSED", "ADSET_PAUSED", "DELETED", "ARCHIVED"})
_AD_HEALTH_FIELDS = ["id", "name", "status", "effective_status", "issues_info"]
```

**The two flags** — a pure helper `_ad_health_flags(ads: list[dict], thresholds) -> list[dict]`
(unit-testable with hand-built ad dicts, no reader), returning 0–2 flags:

- `ads_disapproved` — count of ads with `effective_status == "DISAPPROVED"`. Severity **high** (a
  disapproved ad is a blocked/policy problem burning nothing but delivering nothing). `current` =
  count, `detail` = "{n} of {total} ads are DISAPPROVED".
- `ads_not_delivering` — count of ads the operator **intends to run** (`status == "ACTIVE"`) whose
  `effective_status` is **not** delivering and **not** a deliberate pause and **not** already counted
  as disapproved: `status == "ACTIVE" and effective_status not in (_AD_DELIVERING | _AD_PAUSE_STATUSES
  | {"DISAPPROVED"})`. This residual-with-exclusions definition catches `WITH_ISSUES`,
  `PENDING_REVIEW`, `PENDING_BILLING_INFO`, `PREAPPROVED`, and any future block status while excluding
  parent/self pauses (a paused ad is intentional, not a stall). Severity **medium**. `current` =
  count, `detail` = "{n} of {total} ACTIVE-configured ads are not delivering (blocked/pending)".

Both flags follow the `_flag` shape (`account_discovery.py:1202`) with `baseline/delta/delta_pct =
None` (ad-health is a point-in-time count, not a window delta). A flag fires only when its count `>=
1`; a threshold knob (`ad_health_min_count`, default 1) lives on `AttentionThresholds` for symmetry
but defaults to 1 (any disapproved/stalled ad is worth surfacing on an already-flagged account).

**Attach → recompute severity → re-sort.** Ad-health flags only ever attach to already-flagged
accounts (that is the fan-out gate), so no re-bucketing between flagged/informational is needed — but
they CAN raise an account's severity (a medium-only account with disapproved ads → high). After
attaching, recompute each touched entry's `severity` (max over all flags) and **re-sort the flagged
list** with the existing key (severity desc, |normalized-spend delta| desc, id asc) so the promotion
is reflected deterministically.

**Errors + transparency.** Per-account ad-enumeration failures isolate into `errors` tagged
`{"stage": "ad_health", …}` (an ad read failure never fails the whole call, mirroring the budget
fan-out in `pacing_report`). Add `ad_health_scanned_count: int` to the result (how many accounts were
fanned into) so the cost is legible.

**Documented limitation (out of scope, do not build here).** An account that is window-over-window
clean AND on-pace but has disapproved ads will NOT be ad-scanned (it never became flagged), so its
disapprovals stay hidden. This is the deliberate cost/completeness tradeoff the ticket asks for. A
full-fleet unconditional ad-disapproval scan is a possible future enhancement, explicitly not part of
this ticket.

**MCP wrapper** (`mcp_server.py:556`): add `include_ad_health: bool = False`, pass through. Update
`DISCOVERY_TOOL_DESCRIPTIONS["flag_accounts_needing_attention"]` (`mcp_server.py:454`): document the
opt-in ad-level `ads_disapproved` (high) / `ads_not_delivering` (medium) flags and that ad reads are
issued ONLY for already-flagged accounts (bounded cost).

## Read cost (documented)

Default (`include_ad_health=False`): no ad reads — hard regression guard. With
`include_ad_health=True`: `+ len(flagged)` ad enumerations (each may paginate). Because the fan-out is
gated on the flagged set (never the full scope), a fleet where only 3 of 200 accounts surface pays 3
ad enumerations, not 200.

## Edge cases & interactions

- **`include_ad_health=False` is byte-identical to the prereq's output** — no `iter_paginated` calls;
  assert the reader recorded none.
- **No flagged accounts** → no ad fan-out at all; `ad_health_scanned_count == 0`.
- **Flagged account with 0 ads** → no ad-health flag; still counted in `ad_health_scanned_count`.
- **All ads deliberately paused** (`PAUSED`/`CAMPAIGN_PAUSED`/`ADSET_PAUSED`) → no `ads_not_delivering`
  (deliberate pause ≠ stall).
- **Disapproved ads** → `ads_disapproved` (high); a DISAPPROVED ad is NOT double-counted in
  `ads_not_delivering` (explicitly excluded).
- **`status ACTIVE` but `effective_status WITH_ISSUES/PENDING_REVIEW`** → `ads_not_delivering` (medium).
- **`status PAUSED` but `effective_status` odd** → not counted (operator turned it off).
- **Severity promotion:** a medium behavior/pacing account + `ads_disapproved` → `high`; the flagged
  list re-sorts to reflect it (determinism preserved).
- **Ad-health only over flagged accounts:** an informational (`newly_active`) or clean account is never
  ad-scanned even with disapproved ads (documented limitation).
- **Composition with `include_pacing`:** pacing can PROMOTE a clean account into flagged, which then
  becomes eligible for ad-health scanning. Order: behavior → pacing → finalize flagged →
  ad-health fan-out → attach → recompute severity → re-sort. Test both opt-ins on together.
- **Per-account ad-enumeration failure** → error tagged `stage:"ad_health"`, other accounts unaffected.
- **Determinism:** identical inputs → identical flags/order regardless of fan-out completion order
  (assembly on the main thread over the input-ordered results, as elsewhere in this module).
